# MVP stage 1 plan

Approved by Shlomi on 2026-11-01 (draft r4), including decisions D1 to D8. The status of each step is at the end.

Goal: Shlomi's own Windows PCs run an unsigned agent that reports to the production server; Shlomi signs in to an admin panel, sees agents and sites on an internal map; the server detects provider and infrastructure outages; the agent tells its user whether a fault is at home or at the provider. Signing and customer endpoints (stage 2) are out of scope.

Baseline: `main` at 17a1339; the contract has only `GET /api/agent/health`, protocol version 1. Stage 1 extends version 1. From the first deployment on: new fields are optional, a breaking change becomes version 2 with version 1 still accepted, and request fixtures of every installed agent build stay in the contract tests.

## Decisions of 2026-11-02

- **Better Auth as is.** Admin sign-in uses Better Auth's own features as documented, with no authentication mechanisms of Mashkif's own. The custom layers built in step 1 and 2a (setup token, reset token and pages, admin lock and queue, bounded body reader on auth routes, auth rate limiter, logger allowlist, route allowlist, session assurance classification) are removed in pull request #11. First admin: Better Auth sign-up, allowed only while no user exists. Lost password: Better Auth's email reset. Lost authenticator: Better Auth's TOTP backup codes. Better Auth reads its secret from `BETTER_AUTH_SECRET`, which replaces `MASHKIF_APP_KEY`. Where Better Auth's behavior is weaker than a promise below (idle timeout, user verification at passkey sign-in), the promise changes, not the code.
- **Settings in the admin panel.** Every setting is editable in the admin panel with a default. An environment variable may also set it; it then overrides the stored value and the panel shows the field locked. Only values the server needs before it can read its settings stay environment-only: the database connection, file paths, Compose wiring, and `BETTER_AUTH_SECRET`. The public URL (`BETTER_AUTH_URL`, which replaces `MASHKIF_PUBLIC_URL`) and the trusted proxies moved to the panel under this rule; extra trusted origins, the session length, and SMTP were added under it. A stored SMTP password is encrypted with Better Auth's `symmetricEncrypt`.
- **SMTP.** The server sends email through SMTP (Better Auth password reset and email change now, notifications later).

## Step 1: admin sign-in

Reworked on Better Auth as is (decisions of 2026-11-02). Mashkif configures Better Auth's documented options and adds only what Better Auth cannot do.

- Better Auth 1.7.12 with the Drizzle adapter (`transaction: true`, so Better Auth's own flows such as a password reset run in its transactions), and the `username`, `twoFactor`, and `@better-auth/passkey` plugins, pinned to one version.
- First admin: the setup page calls Better Auth sign-up with a username, an email address, and a password. A `databaseHooks.user.create.before` hook refuses sign-up once a user exists; a one-row database constraint on `auth_user` backs it up. Sign-up signs the admin in.
- TOTP is mandatory: one middleware admits Mashkif's admin API (`/api/admin/*`, except `/status`) only with a Better Auth session whose user has TOTP enabled. Better Auth's own routes (`/api/auth/*`) enforce their own requirements. A session without TOTP is sent to the enrollment page, which shows the backup codes once.
- Lost authenticator: TOTP backup codes (10, each works once), regenerated on the account page with the password; sign-in offers a backup code instead of the TOTP code. Lost password: Better Auth's reset by email, with a link valid for one hour that works with or without a session; a reset ends every session and keeps TOTP and passkeys. Email change: Better Auth sends a link to the new address, and the change takes effect when it is opened.
- Passkeys: registration asks for user verification and needs a fresh session; sign-in uses the plugin defaults.
- Sessions: Better Auth's `expiresIn` from the session length setting (default 12 hours), never extended. No idle timeout.
- Rate limits: Better Auth's, enabled in every environment, in memory: 100 requests per minute, its built-in rules, and 5 per 5 minutes on username sign-in, TOTP and backup code verification, and password reset requests.
- Client address: Better Auth reads `X-Forwarded-For` with `trustedProxies` from the trusted proxies setting. Cookies: Better Auth's defaults, Secure when the public URL is HTTPS. Origins: the public URL, the extra trusted origins setting, and `BETTER_AUTH_TRUSTED_ORIGINS`; Mashkif's admin API also checks the Origin header on every mutation.
- Email: SMTP through `nodemailer` (pinned), TLS required, settings read for each email. The reset and verification emails are short, in Hebrew and English.
- Audit log: sign-up, sign-ins, failed sign-ins, sign-out, TOTP, backup code, passkey, password, and email changes, and password reset requests and outcomes, written from Better Auth's `hooks.after`, plus every admin change.
- Web: `/admin` (setup, sign-in with password and TOTP or a backup code, or a passkey; TOTP enrollment; forgot password; reset password; account with email, backup codes, and passkeys), Hebrew and English, light and dark, code-split from the public bundle.

## Decisions of 2026-11-03

- **Open enrollment (replaces D2).** A user installs Mashkif, and nothing else is needed: no enrollment key, no token to create, no parameters. On its first start the agent creates its own 256-bit token and a random install ID, saves both, and registers without a key. A silent install for GPO or Intune is the same MSI with `/qn` and no properties; `SERVER_URL` stays for development only. Enrollment keys are removed everywhere: the table, the code, the admin page, the contract, the tray, and the MSI. No agent was installed in the field and production never ran, so the contract changes in place; the examples rule for every agent build stays.
- **Trust tier `low`.** Tiers are trusted, normal, low, suspicious, and blocked. A new agent starts at the tier the admin sets for new agents (default `low`). A low agent reports and is stored and shown like any other, but counts in no outage (step 4) until it is promoted. A low agent becomes normal when it is not revoked, reported on at least the configured number of distinct UTC days (server time; default 7, from 1 to 90), and sent a heartbeat in the last 24 hours; the promotion is audited with the actor `system`. An admin who sets `low` from another tier restarts the trial; to hold an agent back for good, the admin uses `suspicious`.
- **Capacity.** New registrations are limited per site (default 10 per 10 minutes) and across all sites (default 200 per hour); a repeat of an existing registration is never limited. The global limit is a denial-of-service tradeoff: whoever uses it up delays new installations, which retry by themselves, while registered agents are not affected; Shlomi can raise it or close registration. Events are limited per agent and hour by count (default 2,000, and 200 for a low agent); events past the budget are deferred and stay on the PC. There is no audit entry per public registration. Agents that registered and never sent a heartbeat are deleted after a period (default 30 days); revoked agents are never deleted, so their token keeps getting `agent_revoked`. All of these are admin panel settings.
- **Revoke, rejoin, and 401.** A revoked agent stops reporting; its tray offers "join again", which registers a new identity on the user's request only. When the server no longer knows a token (401, for example after a restore or a cleanup), the agent registers a new token with the same install ID by itself, at most once an hour, and keeps its old identity until that succeeds. A token whose agent row is missing gets 401; only an explicit revoke gives `agent_revoked`.
- **EXE installer.** A WiX Burn bundle wraps the same English MSI, so Explorer offers "Run as administrator"; the MSI stays for GPO and Intune. It is its own pull request after the agent. Shlomi decided the details on 2026-11-03: WiX 7.0.1 for both installers with the OSMF EULA accepted, one EXE with an English window, unsigned CI artifacts kept for 7 days, and "do not mix" for every EXE and MSI combination except an EXE upgrade, a newer EXE over the English or the Hebrew MSI, and a direct MSI repair under the EXE. He also decided that the MSI upgrade ignores the language (`IgnoreLanguage`), so a newer installer replaces an older one of the other language; no release exists yet, so no installed base is affected.
- **Pull requests.** (A) contract, server, and admin web; (B) the agent (pull request #13 reworked on top of A); (C) the EXE bundle.

## Step 2
: registration, heartbeat, and backfill (three pull requests)

**2a server and admin**

- Admin: enrollment keys (label, expiry, revoke; shown once, stored hashed; removed by open enrollment on 2026-11-03); agents with last seen, version, site address, ASN and organization, area, infrastructure, trust tier (trusted, normal, suspicious, blocked; low added on 2026-11-03), label, revoke.
- `register`: the agent creates its 256-bit token and saves it first, then sends a random install ID, the token, and versions (until 2026-11-03 also the key, which one transaction used). One transaction creates the agent; a retry with the same install ID and token succeeds again, so a lost response or a crash is harmless. The server stores only the token hash. No hostname or user name.
- `heartbeat`: sequence, area cell or unknown, infrastructure, the interval the agent is using, round trip, DNS time. The response carries a sync ID, server time, and the next interval. Until the agent reports using the interval last sent, silence is judged by the larger of the two, so neither a lost response nor a change in either direction makes an agent look silent.
- `events`: connectivity lost and restored, shutdown, sleep, resume, service stop. Each has a durable ID, the boot ID, and the sync ID of the last heartbeat response the agent received, with the time elapsed since then on the monotonic clock, so wall-clock changes do not move it. The server computes the time from the server time it recorded for that sync ID. An event with no sync in the same boot (a reboot while offline), outside the range between the last heartbeat before the gap and the receive time, or older than 7 days is marked "time uncertain" and does not refine history. A late event never changes the current state of an agent with a newer heartbeat. The server answers per event, so one bad event never blocks a batch.
- Limits: body at most 64 KB and 500 events; rate limits by token, and by address only for `register`; 429 with `Retry-After`.
- Client address: `X-Forwarded-For` only when the TCP peer is in `MASHKIF_TRUSTED_PROXIES` (CIDR list), right-most untrusted address. Better Auth's own client address handling (sign-in rate limits) is configured from the same trusted proxies but is separate; without trusted proxies it applies its own documented behavior. Deployment notes recommend a network shared only by Traefik and the app.
- Area: a resolution 7 cell whose center is outside the service area is stored as unknown. An area that Shlomi assigns is stored separately and wins until he clears it.
- Provider table grouping ASNs, managed by the admin, empty in the repository.
- Retention: raw heartbeats and events kept for an admin setting (default 30 days, at least 8), deleted hourly in resumable batches. Outage records keep their own summary and survive this deletion. IP address retention, audit, and backups are separate policies.

**2b agent core**

- `%ProgramData%\Mashkif\state` grants access only to SYSTEM, Administrators, and the service SID (the service runs as LocalService); atomic writes.
- Registration (decisions of 2026-11-03, which replace the enrollment key of the approved text): the service registers by itself at its first start; a revoke or a changed server stops reporting until the user chooses "join again" in the tray, and a 401 re-registers the same install ID by itself, at most once an hour. The token never leaves the service.
- `SERVER_URL` (default `https://mashkif.co.il`); HTTP only to loopback, for development. Backoff with jitter on failure.

**2c agent resilience**

- Connectivity probe every 15 seconds, also offline; transitions, shutdown, sleep, and resume recorded.
- Offline queue: append-only, checksummed lines, a torn last line dropped; a record is removed when the server accepts or rejects it, or when it passes 7 days or the size cap (oldest first, with a dropped count sent later).
- Named pipe: refuses network clients, accepts interactive users. Commands: status and rejoin (2b), then set area cell, set infrastructure, and run diagnosis. No token, no coordinates. The tray checks that the server end is the Mashkif service.
- The queue keeps an event the server answers `deferred` (the agent's hourly event budget is used up, decisions of 2026-11-03) and sends it again after `retryAfterSeconds`; only `accepted`, `duplicate`, and `rejected` remove it.

**Tests for step 2:** racing and interrupted registrations, lost responses, interval increases and decreases with a lost response, a dummy MSI key absent from the registry after registration and not rewritten by repair or upgrade, IPv6 /64 and address changes, spoofed `X-Forwarded-For`, oversize and mixed batches, clock jumps, future times, a lost heartbeat response, and a reboot while offline, retention batches with outage history kept, ACLs after install, repair, and upgrade, pipe access from a standard account, a second session, and the network, queue crash mid-write and overflow, and a live MSI run on a real PC with the network unplugged and a sleep.

## Step 4: detection behind `DetectionEngine`

- `evaluate(now)` reads through a storage port; other code depends only on the interface. Runs every minute.
- Eligible agents are normal and trusted agents on sites that are not blocked. A low agent (a new agent in its trial, decisions of 2026-11-03) is stored and shown on the map but counted in no silent sites and no baseline; it neither opens nor closes an outage until it is promoted. A site is up when an eligible agent sent a heartbeat within three of its intervals; planned offline when every eligible agent's latest record is a shutdown or sleep event later than its last heartbeat; otherwise silent. A site's area and infrastructure come from most of its eligible agents active in the last hour, ties to the most recent, and a silent site keeps its last values. A group's baseline is its sites that were up or silent in the previous hour; a site with no eligible agent in the last hour is not observed and joins no baseline. Thresholds are plain counts of distinct sites, no weights.
- Groups: (provider, H3 parent at resolution 5) and (infrastructure, resolution 5).
- An outage opens when silent sites reach a minimum count and a ratio of the group's baseline and went silent within a correlation window. Its reference sites are frozen at opening; it closes when a recovery ratio of them is back, or becomes "no longer observed" after a maximum time.
- Collection gap: only direct evidence of the server not ingesting (process start, database errors, an ingest gap) stops outages from opening and marks the window. Wide silence alone opens outages normally.
- Backfill refines history; diagnosis is stored but excludes nothing in v1. Thresholds live in a settings table edited in the admin panel; the repository holds development defaults only. Outages are shown on the map and in a list.
- Verification: deterministic simulations: correlated and scattered silence, a multi-hour partial outage, a full outage of the only provider (opens), the server down while agents are fine (does not open), offices closing at night, one PC asleep while another reports, address changes, backfill, trust tiers. Real-world accuracy is not verifiable with a handful of sites; reported as such.

## Step 5: local diagnosis

- On connectivity loss and on request: default gateway, DNS, an external HTTPS endpoint, the Mashkif server; each probe passed, failed, or not supported. Verdicts: home network, provider or beyond, only Mashkif unreachable, not enough information; "possible power outage" on battery with the gateway gone. Shown in the tray in Hebrew or English and sent with backfilled events.
- Verification: fake probes for each verdict, including VPN and captive portal; live checks on a real PC.

## Stage 2: linking an installation to a user account (recorded, not built)

A tray button opens the browser on the Mashkif site. A signed-in user links the installation on a page; a new user signs up first and then gets the same page. The user's dashboard then shows the installation's status and the data it collected. Ownership is never granted from an install ID alone, because it is not a secret: the link has to prove possession of the agent's token. The install ID stays the same through the 401 cycle; joining again after a revoke creates a new installation identity, so a revoked PC has to be linked again.

Step 1 as built, where it adds to or differs from the text above:

- **Versions:** Better Auth and `@better-auth/passkey` 1.7.12, while n8n-ops uses 1.7.10. 1.7.12 is the newest release older than the repository's seven-day cooldown for new versions; 1.7.13 to 1.7.15 change nothing that Mashkif uses. `nodemailer` 10.3.1.
- **Better Auth behavior that Mashkif accepts** (decision of 2026-11-02: the promise changes, not the code): a password reset or email change request answers success even when no email could be sent, for example while SMTP is not set; only the server log says why. Opening the link sent to a new email address in a browser without a session signs the admin in (Better Auth creates a session; the link only ever goes to an address the signed-in admin chose). Without trusted proxies, Better Auth believes a single-value `X-Forwarded-For` without checking the TCP peer, so the app must stay behind its proxy. Passkey sign-in asks for user verification only as preferred. A lost authenticator together with lost backup codes has no recovery path in Better Auth.
- **Logs:** `onAPIError.throw` hands errors other than API errors to the app's error handler, which logs a database error by name and SQLSTATE only; without it, Better Auth's logger prints failed queries with their parameters (for example a new password hash). A test covers this.
- **Settings at startup:** the public URL, the trusted proxies, and the session length are read once at startup; a change in the panel applies after a restart, and a new session length applies to sessions created after it. The extra trusted origins are read for each request, and the SMTP settings for each email.
- **Email strings:** the Hebrew text of the emails lives in `server/src/mail/strings.he.ts`, added to the Hebrew allowlist.
- **Removed:** the setup and reset tokens, their tables, the `setup-token` and `reset-admin` commands, and `/admin/reset`; the route allowlist and refused fields; the session assurance classification, idle limit, and enrollment repair; the admin lock and queue; the auth rate limiter and logger allowlist; the bounded body reader on auth and admin routes. A forward-only migration drops the token tables and the session policy columns.

Step 2a as built
, where it adds to or differs from the text above:

- **Contract additions:** the heartbeat also carries the boot ID, so the server can tell whether an event's sync ID comes from the same boot; an event from another boot's sync is time uncertain. An events request may carry `droppedEvents`: the boot ID and the cumulative number of events the agent dropped from its queue in that boot (2c sends it). The server keeps the largest count per agent and boot, so a retry counts once. Events carry no wall-clock time. The server ignores unknown fields, stores an infrastructure value it does not know as unknown, and rejects an unknown event kind per event, so a newer agent is not refused as a whole.
- **Batch limits:** 64 KB binds before 500 events: an event with a sync ID is about 180 bytes, so about 350 fit. Both limits are as planned; the agent has to respect whichever it reaches first.
- **Rate limits** (the register limit was replaced on 2026-11-03 by a per-site and a global limit, both panel settings): `register` 10 per 10 minutes per client address, in a limiter of its own; heartbeat and events requests 1,200 per minute per client address, counted before the token is looked up, where a missing or unknown token costs 60 (so 20 bogus tokens use up an address's minute and further requests get 429 without a database query); then `heartbeat` 10 per minute and `events` 30 per minute per agent. Limiter entries exist only per address and per agent. An address that sends bogus tokens also limits the real agents behind it for up to a minute; that is the price of keeping the lookup behind the limit. They are code constants like the sign-in limits, not detection values. The limiter drops expired entries from its oldest end instead of scanning the whole map.
- **Event time:** every heartbeat request, also a retry of the same sequence after a lost answer, gets a new sync ID anchored at its own receive time (a retry is stored once as a sample), because the agent measures elapsed time from the answer it received. Anchors live in `sync_anchor`, apart from raw heartbeats; each agent keeps its newest 1,440 (about one day of heartbeats at 60 seconds), and the heartbeat that creates one deletes the older ones under the agent row lock. An anchor is kept as long as fewer than 1,440 newer anchors exist for that agent, including heartbeats whose responses were lost; after that, events that refer to it are stored as time uncertain. No anchor is created while an agent is offline, so time offline alone never evicts the one it holds, also when its last answer was lost or its reconnect heartbeat comes before the backlog. The elapsed time is at most 400 days, and an event whose time is not a valid date is rejected on its own, so nothing an agent sends fails a batch. An event is time uncertain with a recorded reason: no sync in its boot, an unknown sync ID, a sync from another boot, a computed time after the receive time, or older than 7 days. The lower bound of the range is the sync time itself, because the elapsed time cannot be negative. The agent's current state is the latest event with a certain time that is later than both its latest heartbeat and its current event.
- **Registration:** the key's label becomes the agent's label (superseded on 2026-11-03: there are no keys, and the label starts empty). An install ID belongs to one agent for good; after a revoke, the agent enrolls again with a new install ID and a new token.
- **Trusted proxies:** a setting (default empty, overridden by `MASHKIF_TRUSTED_PROXIES`) that lists addresses and CIDR ranges. The agent API resolves its client address from it with `clientAddressResolver`, which also checks the TCP peer; Better Auth resolves its own from the same list.
- **GeoLite2-ASN:** read with the `maxmind` package, version 5.0.7, pinned. It is the maintained MIT-licensed reader that MaxMind's own Node client (`@maxmind/geoip2-node`) builds on, has no install scripts, and reads a buffer, so Mashkif controls loading. The file is checked every minute and loaded again when it changes; a missing or broken file never stops the server, and a broken replacement keeps the last good database. Readiness still checks only that the file is readable. The settings page shows the database's build date and warns when it is older than 14 days.
- **Area cells:** validated with `h3-js` 4.5.0 (Apache-2.0, the reference H3 library), pinned. The service area (`server/src/geo/service-area.ts`) is a coarse outline of 21 vertices drawn by hand for Mashkif from the coordinates of well-known places, with 10 to 20 km of margin at sea and a few kilometers past the land borders; it contains no third-party data and is AGPL-3.0 with the server. Because it is coarse, it also takes in the West Bank, the Gaza Strip, and a thin strip of the neighboring countries. It is not a statement about borders. An admin-assigned area is entered as an H3 cell for now; step 3 assigns it from the map.
- **Agent writes:** heartbeats, events, and registrations check the agent's state and the blocked ranges again inside their write transaction, under a lock on the agent row and a shared advisory lock on the blocked ranges; revoking, changing the tier, and adding a range take the conflicting locks. So a revoke or block that returned to the admin is never followed by a write.
- **Addresses:** one normalization (`server/src/http/ip.ts`, with `ipaddr.js` 2.5.0, pinned: MIT, no dependencies, the library behind Express's `proxy-addr`) for client addresses, sites, trusted proxies, and blocked ranges. Every IPv4-mapped IPv6 spelling is IPv4, and Node's `isIP` decides strictly what is an address. ASNs are stored as `bigint`, so the full 32-bit range fits.
- **Admin changes:** every change and its audit entries commit in one transaction. Settings updates also hold one advisory lock, so the value an update replaces is the one it read and every change is audited. Revoking an agent and deleting a provider ask for a second click, because they cannot be undone.
- **Retention:** the first run starts a minute after the server, then every hour; each batch deletes up to 5,000 rows and commits, up to 200 batches per table per run, and one run at a time per process. Retention deletes only raw heartbeats and events, nothing that ingest writes concurrently. Dropped-event counters are kept for at most 10 boots per agent: a new boot row evicts the oldest by creation, never the boot of the agent's latest heartbeat. Revoking an agent deletes its anchors and boot counters.
- **Not in 2a:** the "what the agent sends" page, which belongs to the public site.

Open enrollment A as built (contract, server, and admin web), where it adds to or differs from the decisions of 2026-11-03:

- **Contract:** `RegisterRequest` has no `enrollmentKey`; `AgentErrorCode` drops the four `enrollment_key_*` codes and adds `registration_closed`; an event result can be `deferred`, and an events response then carries `retryAfterSeconds` (the time until the stored window ends, at least 1 second). `duplicate` now means only "already stored", and an ID repeated within one request gets the result of its first occurrence. The 401 text describes the hourly re-registration with the same install ID, and the 409 text says never to make a new install ID because of it. The request and response examples (`contracts/examples/`) moved here from pull request #13, with the key removed, a `registration-closed-403` example, and an events response with `deferred`.
- **Registration:** one transaction classifies a request against the existing agents first (the token hash and the install ID are each unique over all rows, revoked ones included): both match and not revoked is 200, both match and revoked is `agent_revoked`, any other match is 409. Only then come the switch and the global limit, so a repeat passes while registration is closed or the global limit is used up. The insert uses `ON CONFLICT DO NOTHING`; a conflict with a concurrent insert classifies again on the committed rows, which always finds the conflicting row because conflicting rows are never deleted. Before any database work, every register request counts against an in-memory pre-limit per site (an IPv4 address or an IPv6 /64) of max(60, the per-site registration limit) a minute, which bounds the unauthenticated database work per site and never caps a per-site limit that the admin raised. The pre-limit decides synchronously on the settings already in memory (the last loaded ones, also when stale, and before the first load the minimum of 60), so no query happens before it and a failed refresh never skips it. Only an admitted request refreshes the in-process settings cache, which is read again after every settings save from the panel in this process and otherwise after at most 5 seconds; the refresh is single-flight (one query shared by all callers), but a caller after a settings save never joins a refresh that started before it and starts its own, and only a refresh that is still current after the save is stored; a failed refresh keeps the last loaded settings. Only a request that would create an agent counts against the per-site and global creation limits; a repeat never does, and a creation attempt whose insert found a concurrent registration (answered 200, 409, or `agent_revoked`) gives its units back, as does a site unit when the global limit then refuses. No audit entry is written for a public registration.
- **Missing versus revoked:** `guardAgentWrite` tells a missing agent row (`agent_missing`, answered 401 `token_invalid`) from a revoked one (`agent_revoked`), for heartbeats and events. Before, a missing row was answered `agent_revoked`.
- **Event budget:** two columns on `agent` (`event_window_start`, `event_window_count`) under the agent row lock that event ingest already takes; the window time is the database `now()` read after that lock, it is initialized when null and moves only forward, and `retryAfterSeconds` comes from the stored window end. `MemoryRateLimitStore` is unchanged.
- **Active days and promotion:** the heartbeat update adds an active day when the UTC date of the receive time differs from `last_active_day`. `server/src/promotion.ts` runs a minute after start and then hourly, in batches of 500 that each commit with their audit entries, at most 20 batches a run, with `FOR UPDATE SKIP LOCKED`. Step 2b as built (agent core, pull request #13 reworked on top of open enrollment A), where it adds to or differs from the text above and the decisions of 2026-11-03:

- **State:** `%ProgramData%\Mashkif\state\state.json`, schema version 1: the install ID at the top level, the identity (server origin, token, agent ID), a pending registration (server origin, token), the identity state (`none`, `active`, `token_rejected`, `revoked`), the time of the last register request, the interval, and the next sequence. A load checks the shape: an identity or a pending registration needs an install ID, a pending registration next to an identity is for the same server, `active` has no pending registration, `token_rejected` has one, and `revoked` has neither. Anything else, JSON that does not parse, or a path check that fails with an error (for example a DACL the service cannot read) is `refused` with `state_invalid`, and the file is left untouched. Writes are atomic, with an explicit protected DACL; the next heartbeat sequence, a new token, and the time of every register request are saved before the request is sent.
- **Paths and ACLs:** the MSI sets protected DACLs on `%ProgramData%\Mashkif`, `logs`, and `state`, and on `HKLM\SOFTWARE\Mashkif\Agent\Service` (the parent of the volatile boot ID key), each with an OWNER RIGHTS entry limited to read control. The service SID type is unrestricted, so the state DACL can name `NT SERVICE\Mashkif`. At start the service refuses a product path or state with a reparse point, an unexpected owner, an unprotected DACL, or any other reader or writer.
- **First start:** the service saves a new install ID and a pending token, then registers them with backoff (5 seconds up to 15 minutes, with jitter). `registration_closed` and `install_id_conflict` are shown in the tray and retried hourly with the same body; `address_blocked` is retried with backoff; `agent_revoked` leaves the agent revoked.
- **401 cycle:** the first 401 keeps the token, sets `token_rejected`, and saves a pending token for the same install ID. About an hour later, and at once after a restart, a heartbeat with the old token goes first: 200 drops the pending token and returns to `active`; another 401 registers the pending token, when the saved time of the last register request is an hour old or later than the clock. 201 or 200 replaces the identity; 409, `registration_closed`, 429, and no answer continue the cycle, and the next step is an hour later, or at the end of that hour when a restart came sooner. A lost register response is sent again at the next step with the same body.
- **Revoke and a changed server:** `agent_revoked`, to a heartbeat or to a register request, discards the tokens and saves `revoked`. An identity or a pending registration for another origin than `SERVER_URL` is `refused` with `server_changed`, and nothing is sent, also no retry of a registration from before the change. In both cases only the pipe command `rejoin` continues: one atomic write replaces the install ID, the identity, and any pending registration with a new install ID and a pending token for the configured server, which the service then registers as a first registration. In any other state `rejoin` answers `not_rejoinable`.
- **Pipe:** `\.\pipe\Mashkif.Agent` in byte mode, a fixed pool of four instances created once at start, the first with `FirstPipeInstance`; when any creation fails, nothing is served, the failure is logged, and the whole pool is tried again 30 seconds later. No instance is closed while the service runs: each one waits for a client, answers it, is disconnected (`Disconnect`, or `DisconnectNamedPipe` for a client that left before the wait completed), and waits again, so the name is always held and no instance after the start joins an existing pipe; a stop disposes the pool. Its DACL denies NETWORK and gives INTERACTIVE only read data, write data, read attributes, and synchronize, which is all the tray client asks for. The tray checks through the service control manager that the pipe server is the running service before it writes. Commands: `status` and `rejoin`; the status carries the state, a reason code, `canRejoin`, the last contact, and the server host, and never a token or the install ID.
- **Tray:** the status line in Hebrew or English, and Join again while `canRejoin` is true. A refused Join again shows a notification with one more string than the plan named (`RejoinFailed`).
- **MSI:** no enrollment key: the property, its component, and the `Enrollment` registry key are gone, so the `Debug=7` warning and the accepted gap P12 of the step 2b plan no longer apply. `SERVER_URL` stays for development and is remembered by repair and upgrade. Uninstall keeps the state and the logs.
- **HTTP:** one `HttpClient` that never follows redirects (a 3xx is `refused` with `server_redirect` and retried hourly), a 30-second attempt timeout, `Retry-After` honored up to an hour, heartbeat backoff never longer than the interval, and a DNS time measured separately within 5 seconds.
- **Install test:** `agent/tests/Mashkif.Install.Tests` runs only on a GitHub-hosted runner, behind the assembly fixture `InstallSafetyGate`, which refuses before any change when the runner is not GitHub-hosted, the process is not elevated, or a Mashkif product, service, `%ProgramData%\Mashkif`, `HKLM\SOFTWARE\Mashkif`, or the test user exists. It installs with only `SERVER_URL` against a loopback test API, checks the SID type, the DACLs, one registration with the saved install ID and token, a standard user (status yes; a pipe server instance and the state no) and a refused network logon, then repair and an upgrade to 0.1.1 (the old ProductCode gone, the identity the same, no second registration), uninstall with the state kept, and the token in no MSI or service log. Cleanup removes only what the test created.
- **Not in 2b:** events, the offline queue, the connectivity probe, the area cell, and the infrastructure choice (step 2c).
